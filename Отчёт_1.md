**Доменная область приложения:**\
&nbsp;&nbsp;&nbsp;&nbsp;1. Клиент получает список блюд.\
&nbsp;&nbsp;&nbsp;&nbsp;2. Администратор управляет меню.\
&nbsp;&nbsp;&nbsp;&nbsp;3. Клиент создает заказ из доступных блюд.\
&nbsp;&nbsp;&nbsp;&nbsp;4. Заказ проходит жизненный цикл от создания до завершения или отмены.\
&nbsp;&nbsp;&nbsp;&nbsp;5. Данные сохраняются в PostgreSQL.



**Стек реализации:**\
Backend:\
&nbsp;&nbsp;&nbsp;&nbsp;1. FastAPI - HTTP API\
&nbsp;&nbsp;&nbsp;&nbsp;2. SQLAlchemy - ORM\
&nbsp;&nbsp;&nbsp;&nbsp;3. Alembic - для миграций\
&nbsp;&nbsp;&nbsp;&nbsp;4. PostgreSQL - база данных\
&nbsp;&nbsp;&nbsp;&nbsp;5. Uvicorn - веб-сервер

Frontend:\
&nbsp;&nbsp;&nbsp;&nbsp;React.js, Vite, Nginx


**Основные сущности доменной области приложения:**
1. MenuItem - позиция меню
    Поле | Назначение
    ---  | ---
    id   | идентификатор
    title | название блюда
    description | описание блюда
    category | категория блюда
    price | цена блюда
    is_available | доступно ли блюдо для заказа
    image_url | ссылка на картинку

2. OrderItem - строка заказа, то есть конкретное блюдо в заказе
    Поле | Назначение
    ---  | ---
    id | идентификатор
    price_at_order | цена блюда на момент заказа
    order_id | ссылка на заказ
    menu_item_id | ссылка на блюдо
    quantity | количество

3. Order - заказ клиента
    Поле | Назначение
    ---  | ---
    id | идентификатор заказа
    customer_name | имя клиента
    customer_phone | телефон клиента
    delivery_address | адрес доставки
    status | статус заказа
    total_price | итоговая сумма заказа
    created_at | дата создания заказа
    items | состав заказа


**CRUD-операции над сущностями:**

1. **MenuItem (позиции меню):**
    - Create: администратор добавляет новую позицию меню через `POST /api/v1/menu`.
    - Read: клиент и администратор получают список позиций через `GET /api/v1/menu`; список можно фильтровать по категории и доступности.
    - Update: администратор изменяет данные позиции через `PUT /api/v1/menu/{item_id}`.
    - Delete: администратор удаляет позицию через `DELETE /api/v1/menu/{item_id}`.
2. **Order (заказы):**
    - Create: клиент создает заказ из доступных блюд через `POST /api/v1/orders`.
    - Read: клиент и администратор получают список заказов через `GET /api/v1/orders`, а конкретный заказ — через `GET /api/v1/orders/{order_id}`.
    - Update: статус заказа изменяется в соответствии с жизненным циклом, включая отмену переводом в `CANCELLED`, через `PATCH /api/v1/orders/{order_id}/status`.
    - Delete: физическое удаление заказов API намеренно не предоставляет, поскольку отмененный заказ должен сохраняться в базе данных для учета и истории.

Состав `OrderItem` создается и читается вместе с заказом: отдельный CRUD-маршрут для строк заказа не требуется, так как они не существуют независимо от заказа.



**Аргументация соответствия каждому из пунктов методологии 12 факторов:**\
1. Кодовая база\
&nbsp;&nbsp;&nbsp;&nbsp; Весь код расположен в Git, поэтому есть общая кодовая база. Из одной кодовой базы можно делать разные развертывания.
2. Зависимости\
    &nbsp;&nbsp;&nbsp;&nbsp; Зависимости backend явно прописаны в requirements.txt, а зависимости frontend - в package.json и package-lock.json.
3. Конфигурация\
&nbsp;&nbsp;&nbsp;&nbsp; Значения, которые меняются между окружениями, передаются через переменные окружения и локальный файл .env, который читается с помощью модуля config.py. Файл .env не включается в Git и не должен распространяться вместе с исходным кодом. Для его формирования используется шаблон .env.example; пошаговые инструкции приведены в README.
4. Сторонние сервисы\
&nbsp;&nbsp;&nbsp;&nbsp; PostgreSQL запускается в отдельном контейнере и не хранит данные внутри контейнера backend, поэтому база данных является подключаемым ресурсом.
5. Сборка, релиз, запуск\
Это требование выполнено, вот так выглядит сборка, релиз, запуск на проекте\
Код из Git\
&nbsp;&nbsp;&nbsp;&nbsp;↓ docker compose build\
Docker-образ
&nbsp;&nbsp;&nbsp;&nbsp;+ локальный .env и docker-compose.yml
&nbsp;&nbsp;&nbsp;&nbsp;↓\
Релиз\
&nbsp;&nbsp;&nbsp;&nbsp;↓ docker compose up\
Запущенные контейнеры

6. Процессы\
&nbsp;&nbsp;&nbsp;&nbsp; Приложения backend и frontend запускаются как Docker-контейнеры без состояния, а база данных работает как отдельный подключаемый ресурс.
7. Привязка портов\
&nbsp;&nbsp;&nbsp;&nbsp; Backend является самостоятельным HTTP-сервисом, запущенным на сервере Uvicorn. Он принимает запросы на порту, значение которого задаётся переменной окружения PORT и публикуется через Docker Compose. Frontend обслуживается Nginx на порту 80, который публикуется наружу через FRONTEND_PORT. Nginx также проксирует запросы /api/ на backend. Таким образом, оба сервиса доступны по сети через привязанные порты и не зависят от внешнего веб-сервера окружения.
8. Параллелизм\
&nbsp;&nbsp;&nbsp;&nbsp; Приложение разделено на процессы, запущенные в Docker-контейнерах. Есть разные типы процессов: backend и frontend. Архитектура допускает горизонтальное масштабирование backend, поскольку backend является stateless-процессом, а данные хранятся во внешней PostgreSQL.
9. Утилизируемость\
&nbsp;&nbsp;&nbsp;&nbsp; Контейнеры можно быстро удалить или остановить без потери данных и нарушения работы бизнес-логики. Данные сохраняются с помощью Docker-тома postgres_data, но выполнение команды с параметром -v удалит и этот том вместе с данными.
10. Паритет разработки и продакшена\
&nbsp;&nbsp;&nbsp;&nbsp; Стек везде одинаковый, а Docker Compose уменьшает различия между разработкой и продакшеном. Зависимости устанавливаются внутри контейнеров, поэтому проект можно одинаково запускать в разных окружениях.
11. Логирование\
&nbsp;&nbsp;&nbsp;&nbsp; Логи из приложения выводятся в stdout, а логи Alembic — в stderr. Docker собирает оба потока, но стандартное хранение логов Docker не является полноценным централизованным хранилищем: при удалении контейнера логи могут стать недоступны, а срок их хранения и объем зависят от настроек Docker. Для production-окружения следует настроить ротацию логов и отправку stdout/stderr в централизованный сборщик, например Loki, ELK или облачный сервис логирования.
12. Административные задачи\
&nbsp;&nbsp;&nbsp;&nbsp; Административная задача в виде миграции БД выполняется с помощью Alembic, а файл env.py настраивает окружение для выполнения миграций.
