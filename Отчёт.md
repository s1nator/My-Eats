# Домашнее задание №2: SLI / SLO / SLA — My Eats

## 1. Описание приложения и выбранных метрик

My Eats: React/Vite → FastAPI → PostgreSQL; просмотр меню и оформление заказов. Локальный запуск — Docker Compose, кластерный — манифесты `k8s/`. 

Уже существовали `prometheus-fastapi-instrumentator`, `prometheus-client`, `/metrics`, бизнес-счётчики заказов и гистограмма времени создания заказа. Backend Pod имеет scrape-аннотации. `guide-vmsingle-values.yaml` включает сбор каждые 15 секунд и Kubernetes discovery с переносом labels Pod в метрики. Новых зависимостей и бизнес-метрик не добавлено.

Используем четыре существующих семейства метрик (больше требуемых трёх):

| Метрика | Назначение |
|---|---|
| `http_requests_total{handler,method,status}` | RBSLO HTTP: доля ответов без 5xx; instrumentator группирует статусы как `2xx`, `4xx`, `5xx` |
| `http_request_duration_seconds_bucket` и `_count` | Доля HTTP-запросов, завершившихся за ≤500 мс; bucket `le="0.5"` уже существует |
| `my_eats_orders_created_total` | Успешные бизнес-попытки оформления заказа |
| `my_eats_order_creation_errors_total{reason}` | Учтённые бизнес-отказы: `items_not_found`, `items_unavailable` |

Дополнительно введена только метрика отдельного пробера `my_eats_probe_success` (Gauge 0/1). `up` — служебная метрика scrape VictoriaMetrics. Селектор backend: `app="backend-1"`, пробера: `app="slo-prober"`; он одинаков для Compose и существующего Kubernetes discovery. При нескольких окружениях добавьте к селекторам namespace/cluster, чтобы не смешивать трафик.

## 2. Формулы SLI, SLO, SLA и error budget

Окно обязательств — скользящие 30 дней, демонстрационные графики — 5 минут. Все отношения вычисляются после суммирования приростов счётчиков по репликам, а не усреднением процентов. `increase` учитывает перезапуски.

| SLI | Формула | SLO за 30 дней | Error budget |
|---|---|---|---|
| HTTP availability (RBSLO) | `(N − N5xx) / N` | ≥99,5% | `0,005 × N` ответов 5xx |
| HTTP latency | `N(длительность ≤0,5 с) / N` | ≥95% | `0,05 × N` медленных ответов |
| Бизнес-успех заказа | `created / (created + known_errors)` | ≥99% | `0,01 × (created + known_errors)` учтённых отказов |
| Доступность API меню (TBSLO) | `Σ good_intervals / Σ intervals` | ≥99,95% | 21,6 минуты недоступности |

HTTP SLI охватывают обработанные `/api/v1/*` запросы, включая проверки меню. 4xx считаются доступными HTTP-ответами; это не успешные заказы. При нулевом трафике RBSLO/latency/business SLI не определены — пустой график, а не фиктивные 100%. Отсутствующий ряд 5xx/known_errors подменяется нулём только при наличии общего счётчика.

Бизнес-SLI учитывает только исходы, уже инструментированные в первом ДЗ: ошибки валидации 422 и необработанные ошибки БД/500 не входят в его знаменатель; 5xx контролирует HTTP SLI, полный отказ — пробер. Это отдельный показатель качества бизнес-операции, зависящий также от клиентских данных. Исходная гистограмма `my_eats_order_creation_duration_seconds` измеряет только сервисный вызов и не используется как полная HTTP latency.

**Предлагаемый SLA:** API просмотра меню (HTTP 200 с JSON-массивом, включая обращение к БД, ≤2 с с точки пробера) доступен ≥99,9% времени за скользящие 30 дней, круглосуточно, без исключения плановых работ. Это учебное предложение, а не заключённый договор. Внутренний TBSLO 99,95% строже внешнего SLA.

30 дней = 43 200 минут = 2 592 000 секунд. SLA error budget: `43200 × (1 − 0,999) = 43,2 минуты = 2592 секунды`. Для примера: после 10 минут подтверждённого простоя осталось 33,2 минуты (76,85%). Внутренний TBSLO: `43200 × 0,0005 = 21,6 минуты`. При миллионе HTTP-запросов допустимо 5000 ответов 5xx; при 10 000 попыток заказа — 100 учтённых отказов.

Для графика времени используется фиксированная сетка: demo — 5 с, 30 дней — 1 минута (43 200 точек, укладывается в стандартный лимит subquery VictoriaMetrics). Это дискретная оценка, короткие простои между проверками могут быть пропущены; месячная агрегация имеет точность порядка минуты. Потеря scrape пробера считается плохим интервалом через `up`; полное отсутствие данных — консервативно 0. На новом стенде прежняя история неизвестна и консервативные месячные значения/бюджет НЕ являются измеренным месячным SLA. Для сдачи показываем работоспособность формул и demo-интервал, для реального SLA нужны полные 30 дней наблюдений. Отсутствие самого VictoriaMetrics требует отдельного внешнего мониторинга.

## 3. Реализация пробера

`monitoring/prober.py`: отдельный процесс/контейнер, только стандартная библиотека Python. Каждые 5 секунд выполняет HTTP GET `/api/v1/menu`, timeout 2 секунды. Успех — HTTP 200 и корректный JSON-массив. Этот endpoint выполняет реальный SELECT в PostgreSQL, поэтому проверяется и доступность БД. Ошибка соединения, таймаут, 5xx, невалидный JSON → 0; успех → 1. `/metrics` отдаёт результат на порту 8001 независимо от backend. До завершения первой проверки отдаётся 503, чтобы не выдать несуществующий результат. Используется монотонное время; период учитывает длительность HTTP-проверки. Отказ backend не останавливает экспорт нулей. Пробер не проверяет frontend/публичный ingress: SLA относится к внутреннему API, а не ко всему пользовательскому пути.

Для Kubernetes добавлены Deployment и ConfigMap-монтирование скрипта (`k8s/monitoring/prober.yaml`); существующие Helm discovery/labels уже подходят. Для Compose — `monitoring/scrape.yml`, scrape 5 с, timeout 3 с. VM хранит данные в отдельном volume.

## 4. PromQL/MetricsQL-запросы для графиков

Все точные выражения находятся в `monitoring/queries.json`, проверяются `monitoring/check.py`. Готовые ссылки с запросами и линиями целевых значений — [monitoring/Графики.md](monitoring/Графики.md). Откройте `http://localhost:8428/vmui/`, выберите Graph, интервал последние 15 минут и шаг 5 с. В каждую панель добавляйте SLI и соответствующий `vector(...)` как две query-строки; целевые линии остаются постоянными.

Для месячного HTTP/latency/business SLI замените `[5m]` на `[30d]`. TBSLO/SLA уже содержат отдельные месячные запросы. SLA — линия обязательства, SLI — фактический показатель; линия SLA сама не доказывает соблюдение договора.

**HTTP availability 5m (%)**

```promql
100 * (1 - ((sum(increase(http_requests_total{app="backend-1",handler=~"/api/v1/.*",status=~"5.."}[5m])) or (0 * sum(increase(http_requests_total{app="backend-1",handler=~"/api/v1/.*"}[5m])))) / sum(increase(http_requests_total{app="backend-1",handler=~"/api/v1/.*"}[5m]))))
```

**HTTP latency <=500ms 5m (%)**

```promql
100 * sum(increase(http_request_duration_seconds_bucket{app="backend-1",handler=~"/api/v1/.*",le="0.5"}[5m])) / sum(increase(http_request_duration_seconds_count{app="backend-1",handler=~"/api/v1/.*"}[5m]))
```

**Order success 5m (%)**

```promql
100 * sum(increase(my_eats_orders_created_total{app="backend-1"}[5m])) / (sum(increase(my_eats_orders_created_total{app="backend-1"}[5m])) + (sum(increase(my_eats_order_creation_errors_total{app="backend-1"}[5m])) or (0 * sum(increase(my_eats_orders_created_total{app="backend-1"}[5m])))))
```

**Probe (0/1)**

```promql
min(my_eats_probe_success{app="slo-prober"} * on(job,instance) up{app="slo-prober"}) or vector(0)
```

**TBSLO availability 5m (%)**

```promql
100 * avg_over_time((min(my_eats_probe_success{app="slo-prober"} * on(job,instance) up{app="slo-prober"}) or vector(0))[5m:5s])
```

**SLA availability 30d (%)**

```promql
100 * avg_over_time((min(my_eats_probe_success{app="slo-prober"} * on(job,instance) up{app="slo-prober"}) or vector(0))[30d:1m])
```

**SLA error budget remaining (minutes)**

```promql
43.2 - (1 - avg_over_time((min(my_eats_probe_success{app="slo-prober"} * on(job,instance) up{app="slo-prober"}) or vector(0))[30d:1m])) * 43200
```

**SLO HTTP availability (%)**

```promql
vector(99.5)
```

**SLO latency (%)**

```promql
vector(95)
```

**SLO order success (%)**

```promql
vector(99)
```

**SLO probe availability (%)**

```promql
vector(99.95)
```

**SLA availability target (%)**

```promql
vector(99.9)
```

**SLI HTTP >= SLO (0/1)**

```promql
(1 - ((sum(increase(http_requests_total{app="backend-1",handler=~"/api/v1/.*",status=~"5.."}[5m])) or (0 * sum(increase(http_requests_total{app="backend-1",handler=~"/api/v1/.*"}[5m])))) / sum(increase(http_requests_total{app="backend-1",handler=~"/api/v1/.*"}[5m])))) >= bool 0.995
```

Официальная документация: [scrape и vmui](https://docs.victoriametrics.com/victoriametrics/scrape_config_examples/), [API и модель запросов](https://docs.victoriametrics.com/victoriametrics/keyconcepts/). Запросы не требуют Grafana, vmalert или recording rules.

## 5. Изменения приложения

В `backend/src/main.py` добавлена middleware-инъекция только при одновременных `ENVIRONMENT=development` и `SLO_DEMO=1`. Заголовок `X-Demo-Fault: error` возвращает 503; `X-Demo-Fault: delay` добавляет 800 мс к HTTP-запросу. Без обоих флагов middleware не регистрируется. `/metrics` и `/health` исключены из HTTP-метрик, чтобы scrape и технические проверки не улучшали SLI. Пробер обращается к меню без demo-заголовков. `/health` помечает только явно включённый demo-режим полем `mode=slo-demo`; генератор проверяет его до записи меню/заказов и отказывается работать с обычным backend.

Для раннего demo-ответа middleware сохраняет найденный маршрут в scope, чтобы instrumentator использовал корректный handler. Demo-ошибки заказа генерируются отдельным настоящим запросом с несуществующим menu_item_id, чтобы вырос существующий `my_eats_order_creation_errors_total`. Отказ до бизнес-обработчика не выдаётся за учтённую бизнес-ошибку.

`docker-compose.slo.yml` применяется явно поверх базового Compose: проект `slo-demo`, отдельные БД/volumes, миграция Alembic перед запуском, пробер и VictoriaMetrics. Production-манифесты backend не переключаются в demo; Helm-конфигурация первого ДЗ сохранена. Имеющиеся пользовательские изменения в requirements, Deployment, VS Code и `.diagnostics` сохранены.

## 6. Инструкция запуска и демонстрации

Нужны Docker Desktop/Engine, Docker Compose и Python 3 на хосте (для скриптов дополнительных pip-пакетов не требуется). Свободные порты 5432/8000/8001/8428. Команды из корня репозитория; если `.env` отсутствует, создайте `cp .env.example .env`. Для demo не меняйте production `.env`, используйте параметры запуска ниже. На машине проверки Docker был установлен, но не запущен; Docker Desktop запущен для реальной проверки.

```bash
# Изолированный проект; --env-file фиксирует demo-порты из шаблона.
export COMPOSE_PROJECT_NAME=slo-demo
export COMPOSE_FILE=docker-compose.yml:docker-compose.slo.yml
# Для всех compose-команд ниже используем шаблон подстановки переменных.
docker compose --env-file .env.example up -d --build db backend prober victoriametrics
# Backend применяет миграции автоматически.
curl -fsS http://localhost:8000/health
curl -fsS http://localhost:8001/metrics
curl -fsS http://localhost:8000/metrics

# 1. Нормальная работа: реальные создание меню, заказы и чтение меню.
python3 monitoring/demo.py normal 45
# 2. 503 + бизнес-отказы 404 (увеличиваются разные метрики).
python3 monitoring/demo.py error 45
# 3. Ответы успешны, но медленнее 500 мс.
python3 monitoring/demo.py delay 45
# 4. Полная недоступность: пробер/VM продолжают работать.
docker compose --env-file .env.example stop backend
sleep 20
curl -fsS http://localhost:8001/metrics  # my_eats_probe_success 0
# 5. Восстановление.
docker compose --env-file .env.example start backend
python3 monitoring/demo.py normal 45
# VM может отображать самые свежие данные с задержкой около 30 с.
sleep 35
python3 monitoring/check.py
```

До первого demo-запроса дождитесь `curl -f http://localhost:8000/health` (при холодной сборке запуск занимает время). В скринкасте используйте второй терминал для показа графиков/пробера. У HTTP availability падение при 503; у business success — при 404; у latency — при delay; у бинарного пробера — 1→0→1 при остановке/start. Во время полного отказа счётчики запросов не растут: это не означает доступность, поэтому нужен TBSLO. После восстановления бинарная доступность возвращается быстро, а 5-минутные проценты восстанавливаются постепенно; для полного выхода ошибок из окна запустите `python3 monitoring/demo.py normal 330`.

`monitoring/check.py` проверяет все query_range на статус success и наличие конечных числовых точек, сохраняет диапазон/последнее значение в `monitoring/verification.json` и ссылки в `monitoring/Графики.md`. Отсутствие трафика может корректно дать пустой request-SLI — сначала выполните normal. Вновь запущенный VM не имеет 30 дней истории: отрицательный консервативный месячный бюджет не является доказательством реального месячного нарушения.

Проверка БД (необязательно): `docker compose --env-file .env.example stop db`, через ≥7 с пробер должен быть 0; затем `docker compose --env-file .env.example start db`, дождитесь healthy и 1. Остановка стенда без удаления данных: `docker compose --env-file .env.example down`. Demo создаёт заказы только в БД проекта `slo-demo`; существующие volumes других проектов не затрагиваются.

Подключение пробера к существующему Kubernetes/Helm (кластер должен уже работать):

```bash
kubectl create configmap slo-prober --from-file=prober.py=monitoring/prober.py --dry-run=client -o yaml | kubectl apply -f -
kubectl apply -f k8s/monitoring/prober.yaml
# Если VictoriaMetrics ещё не установлен, используйте существующие values:
helm repo add vm https://victoriametrics.github.io/helm-charts/
helm repo update
helm upgrade --install vmsingle vm/victoria-metrics-single -f guide-vmsingle-values.yaml
kubectl get svc  # найдите HTTP service VictoriaMetrics
# kubectl port-forward svc/<имя-service> 8428:8428
```

ConfigMap, Deployment и backend должны находиться в одном namespace. Kubernetes здесь не запускался: `kubectl config current-context` не настроен. Для dev-инъекции в Kubernetes используйте отдельный namespace с отдельной БД, собственный образ с текущим кодом и два demo-флага; production Deployment изменять не требуется. Основная воспроизводимая демонстрация выполнена через Compose.

- Проверены четыре комбинации ENVIRONMENT/SLO_DEMO: middleware активна только development/1; в production/1 отключена.
